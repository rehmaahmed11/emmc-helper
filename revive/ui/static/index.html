1. What is the phone doing right now?

Read-only detection. Revive never writes to a device without a validated plan and an explicit confirmation.

2. Order of operations that does not brick phones

Follow this every time. Skipping step 1 is how data is lost.

#StepWhy
1Back up what still readsDying eMMC only gets worse; a backup is the only irreplaceable thing here
2Identify the chip and the security stateDecides whether you need an auth file before you even try to flash
3Verify the firmware matches the modelWrong-model firmware is the number one hard-brick cause
4Read the dry-run planSee every write, its size and target before it happens
5Flash, then verify the read-backA flash that is not verified is a hope, not a repair

Firmware package check

Point at the extracted firmware folder (or a single file). Revive works out the format, validates every file, and prints a dry-run plan.

Examples: SP Flash Tool package (scatter), Qualcomm EDL package (rawprogram XML), Unisoc .pac, a single boot.img, a raw disk dump.

Full-dump surgery

Read a full-flash dump: partition table, what each partition contains, health warnings, and extraction with checksums.

Convert / expand

Sparse ↔ raw, LZ4 expansion, trimming zero tails, boot image extraction.

super.img (dynamic partitions)

See what is inside a modern system image before you trust it.

Backup integrity

A backup you never verified is not a backup. Write a manifest of SHA-256 hashes, verify it later.

Sparse image verify

Check a vendor sparse image's declared checksum against its actual contents - catches truncated downloads.

Error decoder

Paste the tool's log or just the code (e.g. 2005, 0xC0060001, STATUS_EXT_RAM_EXCEPTION). You get what it means, why it happens, and what to do - in that order.
